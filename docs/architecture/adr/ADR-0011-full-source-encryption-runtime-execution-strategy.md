# ADR-0011: Full-Source Encryption / Runtime Execution Strategy

* Status: Accepted
* Date: 2026-08-16
* Deciders: RunStack Ember
* Scope: Source Layer, Runtime Layer, Packaging Layer
* Related: ADR-0002, ADR-0004, ADR-0007, ADR-0009, ADR-0010

## Context

RunStack Ember already provides source-level transformations intended to increase the cost of casual inspection and reverse engineering of distributed PHP source.

`StringProtectionPass` protects individual string literals with AES-256-GCM. The encryption key is generated per build invocation and embedded in the generated source alongside the ciphertext. Its threat model explicitly does not claim key secrecy against an attacker capable of inspecting the generated PHP.

`IntegrityVerificationPass` detects modifications to the generated source by embedding a SHA-256 digest of the final representation and verifying it at runtime.

The next candidate source transformation is `EncryptionPass`.

Unlike `StringProtectionPass`, which replaces individual literals while leaving the surrounding PHP source intact, full-source encryption would replace the protected PHP source itself with a small executable loader.

The resulting distributed file would therefore contain:

1. an encrypted representation of the original PHP source;
2. the information required to decrypt it;
3. a loader capable of reconstructing the plaintext;
4. a mechanism for executing that reconstructed PHP.

This is materially different from the existing AST-oriented passes.

The pass remains a `SourceCode -> SourceCode` transformation because its output is still valid executable PHP. However, the transformation does not meaningfully operate on the user's AST: the original source becomes an opaque encrypted payload and is replaced by a loader.

The decision therefore crosses the boundary that the project has previously used to identify the need for a Runtime Layer.

## Decision

RunStack Ember will support full-source encryption through a self-contained runtime loader in the first implementation.

The `EncryptionPass` will:

* receive normal `SourceCode`;
* encrypt the complete protected PHP source;
* replace that source with a small executable loader;
* keep the generated output as valid PHP;
* decrypt the source at runtime;
* materialize the decrypted source into a temporary PHP file;
* execute it using `include`;
* remove the temporary file immediately after execution.

The first implementation will not use `eval()`.

The first implementation will not require the protected application to install RunStack Ember as a Composer runtime dependency.

The loader generated by the pass will therefore be self-contained.

## Runtime execution mechanism

### Decision

Use temporary-file materialization followed by `include`.

The decrypted PHP source will exist on disk only for the execution window required by the loader.

The temporary file will be removed immediately after the `include()` operation completes.

### Rationale

Using a temporary PHP file preserves behaviour that is naturally associated with normal PHP file execution more closely than `eval()`.

In particular, this approach provides a more conventional environment for:

* `__FILE__`;
* `__DIR__`;
* stack traces;
* PHP file-related diagnostics;
* opcode compilation;
* debugging behaviour.

`eval()` avoids filesystem materialization, but that advantage is not sufficient to justify making it the v1 execution mechanism.

The project therefore accepts the filesystem cost in exchange for more conventional PHP execution semantics.

## Temporary-file lifecycle

The v1 loader will use a fresh temporary path for each execution.

The decrypted source will not be stored under a stable, reusable application path.

After execution, the temporary file will be removed.

This deliberately means that v1 does not attempt to make the decrypted representation persistent for OPcache reuse.

The resulting recompilation overhead is accepted as a v1 trade-off.

A stable decrypted cache may be considered in a future version if profiling demonstrates that the compilation overhead is materially significant.

Performance optimisation is therefore deferred until there is evidence that it is necessary.

## Key generation and storage

The encryption key will be generated anew for each build.

The key will be embedded in the generated loader.

The v1 design does not introduce an external key-management service, environment-provided encryption key, licensing server, or other external key source.

This follows the existing threat-model boundary established by `StringProtectionPass`.

The presence of AES-256-GCM does not imply that the key is secret from an attacker who possesses the generated loader.

An attacker capable of inspecting the loader can obtain the key and reproduce the decryption process.

The purpose of full-source encryption is therefore not cryptographic key secrecy.

Its purpose is to prevent the distributed file from exposing the protected PHP implementation directly as readable source.

## Threat model

Full-source encryption is explicitly limited to the following protection objective:

> Remove the PHP implementation in plaintext from the distributed file while increasing the cost of casual inspection and static extraction.

It does not claim resistance against an attacker capable of executing or analysing the loader.

An attacker capable of executing the loader necessarily has access to the mechanism required to decrypt the source.

The design also does not claim protection against:

* memory inspection;
* runtime instrumentation;
* interception of the decrypted source;
* modification of the loader itself;
* extraction of the decryption key from the loader;
* observation of the temporary decrypted PHP file while it exists.

The temporary-file strategy therefore introduces a deliberate, short-lived plaintext exposure window on disk.

That exposure is accepted for v1.

## Authentication and tamper detection

AES-256-GCM provides authenticated encryption.

Consequently, when the encrypted payload is modified, the authentication tag should cause decryption to fail rather than producing accepted plaintext.

Full-source encryption therefore provides tamper detection for the encrypted payload itself without requiring a separate SHA-256 integrity check for the ciphertext.

This changes the role of `IntegrityVerificationPass`.

`IntegrityVerificationPass` must not automatically be considered redundant merely because GCM authenticates the encrypted payload.

Its precise role when combined with full-source encryption remains an architectural question.

In particular, the project must distinguish between:

1. authenticity of the encrypted distributed payload;
2. integrity of the decrypted temporary representation;
3. detection of modifications to the loader;
4. broader runtime integrity guarantees.

No decision is made in this ADR to remove `IntegrityVerificationPass` from encrypted editions.

That decision requires a separate evaluation.

## Interaction with `IntegrityVerificationPass`

The relative ordering of the two passes is constrained by what each pass is intended to protect.

If `IntegrityVerificationPass` runs before full-source encryption, its generated integrity check becomes part of the encrypted plaintext.

The encrypted loader subsequently becomes the distributed representation.

In that configuration, the integrity check is executed only after the encrypted source has been decrypted and materialized.

If `IntegrityVerificationPass` runs after full-source encryption, it can only verify the loader produced by `EncryptionPass`, rather than the original protected application source.

That distinction must not be hidden by the generic term "integrity".

Therefore:

> `EncryptionPass` must not be added to an edition until the intended role and ordering of `IntegrityVerificationPass` have been explicitly established.

The present ADR records this as an open architectural question rather than inventing a justification for one ordering.

## Runtime Layer

The `EncryptionPass` is the second concrete case identified by the existing Runtime Layer checkpoint.

The first generation of passes can remain self-contained because their runtime behaviour can be injected directly into the resulting source:

* `StringProtectionPass` injects inline decryption expressions;
* `IntegrityVerificationPass` injects an inline integrity check;
* `ControlFlowPass` injects inline control-flow guards.

Full-source encryption is different.

It introduces a complete decrypt-and-execute mechanism whose natural responsibility is runtime execution rather than AST transformation.

Therefore this ADR considers the Runtime Layer checkpoint satisfied.

However, the first `EncryptionPass` implementation will not yet introduce a shared Runtime API.

The loader will remain self-contained.

The Runtime Layer will be opened as an explicit architectural component when the implementation demonstrates a concrete need for shared runtime behaviour.

This avoids creating an abstraction merely because the roadmap predicts that one may eventually be useful.

## Packaging Layer

The generated encrypted PHP file must not require the protected application to depend on RunStack Ember at runtime.

The v1 loader is therefore self-contained.

A future Packaging Layer may provide shared runtime support files when sharing the runtime implementation between generated outputs becomes beneficial.

Such packaging would be an implementation and distribution mechanism, not a Composer runtime dependency imposed on the protected application.

## Pass classification

`EncryptionPass` will implement `Pass` directly rather than extending `AbstractAstPass`.

The reason is structural.

The pass does not transform the user's AST in the same way as:

* `SymbolRenamePass`;
* `StringProtectionPass`;
* `ControlFlowPass`.

It transforms the complete source representation into an encrypted payload plus loader.

Its contract remains:

```text
SourceCode -> SourceCode
```

but its implementation operates on the complete source representation.

This is therefore analogous to the architectural position already occupied by `MinificationPass`, rather than the AST transformation passes.

No new representation type is justified solely by this distinction.

## Ordering constraints

The eventual ordering of `EncryptionPass` must preserve the following principle:

> All transformations that are intended to protect the original PHP source must complete before the source is encrypted.

Once `EncryptionPass` replaces the original source with an opaque encrypted payload, subsequent source transformations cannot meaningfully transform the original application code.

Therefore encryption is a terminal transformation of the protected source pipeline.

The exact final ordering relative to `IntegrityVerificationPass` remains unresolved as described above.

The previously established source transformations can conceptually remain:

```text
symbol-rename
-> string-protection
-> control-flow
-> minification
-> [integrity-verification / encryption ordering to be decided]
```

The final edition ordering must not be activated until the integrity/encryption interaction has been tested end-to-end.

## Non-goals

This ADR does not introduce:

* external key management;
* server-side key retrieval;
* licensing enforcement;
* anti-debugging;
* memory protection;
* persistent decrypted source caching;
* OPcache optimisation;
* a shared Runtime API;
* a mandatory Runtime Composer dependency;
* a new source representation type;
* `eval()` execution.

These may be considered independently in future ADRs.

## Consequences

### Positive

* Distributed PHP source is no longer directly readable.
* The existing AES-256-GCM primitive can provide authenticated encryption of the complete source.
* The loader remains self-contained.
* The protected application does not need RunStack Ember installed at runtime.
* PHP execution remains based on a real file and `include()` rather than `eval()`.
* Runtime caching can be introduced later if performance measurements justify it.
* The Runtime Layer now has a concrete second use case rather than being an abstraction created speculatively.

### Negative

* Plaintext PHP temporarily exists on disk during execution.
* The decrypted file must be removed reliably.
* v1 accepts recompilation overhead caused by a fresh temporary path.
* The encryption key remains recoverable from the generated loader.
* Runtime execution becomes more complex than ordinary PHP source execution.
* `IntegrityVerificationPass` now has a narrower and more complicated relationship with the encrypted representation.
* Debugging and operational behaviour must be tested rather than assumed to be identical to ordinary PHP execution.

## Consequences for the roadmap

The Runtime Layer checkpoint is now considered reached conceptually.

The next implementation step is not immediately writing `EncryptionPass`.

The next step is to turn this ADR into executable architectural constraints through tests covering:

1. complete source encryption;
2. successful decryption;
3. successful execution through a temporary file;
4. temporary-file cleanup;
5. authentication failure after ciphertext modification;
6. loader failure behaviour;
7. namespace preservation;
8. `__FILE__` and `__DIR__` semantics;
9. exceptions and stack traces;
10. interaction with `IntegrityVerificationPass`;
11. ordering within the complete edition pipeline.

Only after those constraints are established should the concrete `EncryptionPass` be implemented.

## Status

Accepted.

Full-source encryption is approved as the next major Source-layer capability, but implementation is gated on the runtime execution and integrity-order tests defined above.

## Addendum (2026-08-21): IntegrityVerificationPass and final pass ordering

The runtime execution and compression tests described above are now implemented and passing (`EncryptionPass`, `EncryptionPassTest`). Two questions this ADR left explicitly open are now closed.

### IntegrityVerificationPass is excluded when EncryptionPass runs

AES-256-GCM is an authenticated cipher: `openssl_decrypt()` fails outright on any modification to the ciphertext, including modification of the loader that wraps it. Running `IntegrityVerificationPass` after `EncryptionPass` would only authenticate the loader, which GCM already authenticates on every decryption attempt; running it before `EncryptionPass` embeds the check inside the encrypted plaintext, where it can only ever verify the temporary file after that file has already been decrypted and written to disk, a narrower and rarer scenario than the tampered-artifact-at-rest case `IntegrityVerificationPass` exists for. Neither position earns its cost.

Decision: `IntegrityVerificationPass` does not participate in any pipeline where `EncryptionPass` also runs. It remains available, unchanged, for editions that do not use full-source encryption.

### Final pass ordering for an encrypted pipeline

The rule this ADR originally implied, "`EncryptionPass` must be the last pass", is stronger than what the project actually needs and is not what the implementation does. The rule that matters is narrower:

> `EncryptionPass` must be the last pass that transforms the protected program. A pass may run after it only if it is provably incapable of inspecting, parsing, or modifying the encrypted payload, operating exclusively on the generated loader's own representation.

`MinificationPass` satisfies this. Unlike `SymbolRenamePass`, `StringProtectionPass`, `ControlFlowPass`, and `IntegrityVerificationPass`, it does not build or depend on an AST of the protected program; per its own pass classification (see "Pass classification" above), it operates on raw PHP text as tokens. When it runs after `EncryptionPass`, the text it receives is the loader, not the protected program, which by that point is opaque ciphertext inside a string literal. `MinificationPass` cannot see through that any more than a human reading the loader's source can.

This is not merely permitted; it is measurably worth doing twice. Running `MinificationPass` once before `EncryptionPass` (shrinking the plaintext that gets compressed and encrypted) and once after (shrinking the generated loader's own boilerplate) are independent, additive savings, not redundant or competing choices:

| Configuration (same fixture, `--lean`, no `IntegrityVerificationPass`) | Final size |
|---|---|
| Neither | 3686 bytes |
| Minify before only | 3366 bytes |
| Minify after only | 2415 bytes |
| Minify before **and** after | **2095 bytes** |

An earlier pass at this comparison concluded minifying before `EncryptionPass` was actively counterproductive; that conclusion came from an experiment that changed two variables at once (it compared "minify before, not after" against "not before, minify after" as if they were opposites) rather than isolating the effect of each position. Measured in isolation, minifying before helps on its own merits: it hands `gzdeflate()` fewer bytes of plaintext to compress. It helps less than minifying the loader afterward, but the two are not in tension.

Decision: the encrypted Source-layer pipeline is

```text
symbol-rename
-> string-protection   (omitted under --lean)
-> control-flow
-> minification         (shrinks the protected program before it is frozen)
-> encryption            (freezes the protected program as an opaque loader)
-> minification         (shrinks the loader's own boilerplate; cannot see the payload)
```

The non-encrypted pipeline is unchanged:

```text
symbol-rename
-> string-protection   (omitted under --lean)
-> control-flow
-> minification
-> integrity-verification
```

Both `minification` steps in the encrypted pipeline are the same pass, `MinificationPass`, run twice with different input; they are not two different passes and are not renamed to suggest otherwise. Any future pass wanting to run after `EncryptionPass` (a hypothetical `LoaderOptimizationPass`, for instance) must justify itself against the same contract `MinificationPass` satisfies here: text/token-level operation on the loader's own representation, no visibility into or modification of the encrypted payload. That justification belongs in this ADR or its own, not assumed by precedent.

### Runtime Layer: still not required

Nothing above requires opening the Runtime Layer. The loader remains fully self-contained, per the original decision in this ADR. The Runtime Layer opens when a second concrete need for shared runtime behavior appears, not preemptively.

### Not yet decided

Whether `EncryptionPass` (with or without `--lean`) is activated in `premium.php` or `enterprise.php` is an explicit non-decision here. That is a product decision, separate from the architecture question this addendum closes, and is deferred to a later ADR or edition change.
